# 实验驱动开发：个人技术探索方法论

## 引言

作为开发者，你是否经常这样：灵光一闪，脑洞大开，立刻开始构建。但过程中频繁被技术卡住——几分钟、几小时、几天，甚至不得不更换技术栈。最终完成度低，计划形同虚设，项目在“边做边查、边学边做”中迷失方向。

这种困境的根源在于：**我们把“探索”和“构建”混为一谈**。当技术路径不明确时，我们需要一套专门的方法来管理探索过程，让“未知”变得可预测、可记录、可决策。

本文档提出的“实验驱动开发”（Experiment-Driven Development）正是为了解决这个问题。它借鉴了科学实验、工程设计、知识管理的思想，将技术探索视为一系列可管理的实验，允许“无结果”作为合法产出，并帮助你在不确定性中做出清晰决策。

这套方法目前由个人实践提炼，欢迎你使用、改进、分享，共同完善。

---

## 一、核心原则

1. **区分探索与构建**  
   - 探索实验的目标是**获得知识**（“A技术能不能实现B？”），而非交付代码。  
   - 构建任务的目标是**产出可用的功能**。两者必须分开管理。

2. **实验必有记录**  
   - 每个实验必须产出结构化报告，包括假设、过程、结论、根因、约束等。  
   - “无结果”也是一种宝贵产出——它排除了错误路径。

3. **失败驱动决策**  
   - 实验失败不是终点，而是生成新约束、收敛候选方案的起点。  
   - 当所有候选方案被排除（空集），触发元级决策，明确下一步（暂缓、转向、重构、学习、终止）。

4. **知识可积累**  
   - 所有实验报告归档，形成个人技术决策库，避免重复踩坑。

## 三、关键实践详解

### 1. 定义实验目标（B）

- **必须是能力目标，而非方案目标**  
  - 错误：“用WebRTC实现实时画板”  
  - 正确：“实现实时画板能力”（技术方案未定）  
- **必须可验证**：定义清晰的验收标准。例如：“两个用户能同时看到对方笔迹，延迟<200ms”。

### 2. 提出假设（A）

- 假设要具体到技术/工具/库：例如“使用WebSocket + Canvas能否实现实时画板？”
- 可选为假设设定优先级：P0（核心）、P1（重要）、P2（次要）。

### 3. 执行实验（时间盒）

- **设定时间盒**：根据复杂度设定2–8小时，最长不超过1天。时间到即停止编码。
- **实验代码可丢弃**：目标是验证可行性，不必考虑代码质量、可维护性。
- **专注假设**：若实验过程中发现需要绕路解决，则视为假设不成立（除非绕路在实验目标之内）。

### 4. 记录结果（实验报告模板）

```markdown
## 实验报告：验证A实现B

### 基本信息
- 实验编号：EXP-XXX
- 日期：
- 假设：A技术能否实现B目标？
- 时间盒：X小时（实际耗时：X小时）

### 实验过程
- 主要步骤：
- 遇到的障碍：
- 采用的尝试：

### 结论
[ ] 可行
[ ] 不可行

### 若可行
- 技术路径简述：
- 关键配置/代码片段：

### 若不可行
- 根本原因：（A技术的哪个具体限制导致失败？）
- 相关证据：（错误日志、性能数据、文档摘录）

### 约束生成
- 由此得出的约束：今后实现B时，不能选用具有以下特性的技术：
  1. ...
  2. ...

### 候选集过滤
- 已知候选技术中，哪些可能满足约束？
  - C：原因
  - D：原因
- 候选集： [ ] 非空（列出） [ ] 空集

### 元级决策（若候选集为空）
- 空集原因：[ ] 技术不成熟 [ ] 个人能力边界 [ ] 问题定义有问题 [ ] 其他
- 决策：
  [ ] 暂缓，等待______成熟
  [ ] 转向，新目标是______
  [ ] 重构问题，将B拆解为______
  [ ] 学习，需要掌握______
  [ ] 终止，结论是______

### 下一步
- [ ] 进行下一个实验：______
- [ ] 执行元级决策：______
```

### 5. 根因分析与约束生成

根因分析要挖掘到技术本质，例如：
- 是API限制？（如浏览器不支持某个特性）
- 是性能问题？（如延迟超过阈值）
- 是生态问题？（如缺少必要依赖）
- 是个人技能问题？（如不熟悉该技术）

约束是具体、可操作的禁止项。例如：“不能使用依赖WebRTC原生API的库，因为需要支持旧版浏览器。”

### 6. 候选集过滤与空集决策

- **候选集**：基于约束，从技术雷达或经验中筛选可能可行的技术。
- **空集**：当没有任何已知技术能满足约束时，触发元级决策。  
  元级决策选项：
  - **暂缓**：等待技术成熟（如新版本发布）。
  - **转向**：放弃B，选择一个更可行的新目标B'。
  - **重构**：将B拆解为更小的子目标，分阶段实现。
  - **学习**：投入时间学习某项新技术，以扩大候选集。
  - **终止**：承认当前条件下不可行，结束探索。

### 7. 知识库管理

- 将所有实验报告归档到一个目录（如 `docs/experiments/`）。
- 为每个报告添加标签：技术栈、目标类型、结论状态。
- 定期回顾，建立“技术决策日志”，总结常见约束和模式。

## 四、与项目管理的结合

探索性工作可以融入传统项目管理中：

- **看板管理**：在“待办”中增加“探索”列，所有尖峰实验任务在此列，完成后进入“决策”列。
- **迭代计划**：每个迭代预留20%时间用于技术探索（特别是存在不确定性的部分）。
- **优先级**：将影响核心功能的技术探索设为最高优先级，优先验证关键假设。

## 五、进阶建议

1. **引入技术成熟度（TRL）评估**  
   参考NASA TRL体系，为每个技术点标记成熟度（1~9级），当TRL不足时，决策更容易。

2. **建立个人技术雷达**  
   定期维护一个清单：尝试过、可行、不可行、待验证的技术，附上约束和结论。

3. **记录否定性知识**  
   将“为什么A不行”写成短文，发布在个人博客或社区，积累个人影响力。

4. **与同行交流**  
   邀请伙伴共同进行“结对探索”，或定期分享实验报告，从不同视角获得新候选技术。

## 六、结语：引玉之砖

这套“实验驱动开发”方法论源于个人实践中的挣扎与思考，目前还处于草创阶段。它尝试填补软件开发中一个空白：**如何系统化地管理技术探索，让“无结果”也成为有价值的产出**。

我把它分享出来，是希望它能成为一块砖，引玉——吸引更多人关注这个话题，共同完善一套真正适合“探索型开发者”的方法论。

如果你有更好的实践、不同的见解，或者将这套方法应用到了你的项目中，非常欢迎交流讨论。我们可以一起，让技术探索不再盲目，让每一次尝试都有所积累。
