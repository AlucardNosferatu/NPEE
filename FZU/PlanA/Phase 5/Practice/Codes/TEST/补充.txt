# 【补充材料：OJ考试环境下测试框架的正确写法】

## 一、背景信息

在**OJ考试环境**中，你只能获得以下反馈：
- 提交代码后，OJ返回运行状态符号：`AC`、`WA`、`RE`、`TLE` 等。
- **无法看到程序的输出内容**、输入数据或中间变量。
- **无法使用断点、步进调试**，也不能在代码中添加打印语句（打印内容不可见，且会干扰输出）。

因此，我们采用一种特殊的内置测试框架：让用户在本地运行代码测试用例，但测试结果必须能通过OJ的状态符号“传递”出来。**唯一可用的信号就是OJ返回的WA和RE**。

## 二、核心设计原则

### 1. 宏开关控制测试模式，默认关闭
- 定义一个宏（如 `#define CASE`），**默认注释掉**。用户本地测试时取消注释，提交OJ时保持注释。
- 正常提交的代码不含任何测试代码，确保AC。

### 2. 多用例选择（可选）
- 通过 `#if CASE == 1` / `#elif CASE == 2` 等分支，为不同测试场景提供独立的硬编码输入数据和预期输出。
- 用户只需修改宏的值，即可快速切换测试用例集。

### 3. 输入重定向（测试模式）
- 测试模式下，将 `cin` 绑定到硬编码的输入字符串流（`istringstream`），模拟键盘输入。
- 核心计算逻辑完全不变，仍使用 `cin` 读取，保证两种模式下行为一致。

### 4. 输出前断言（单次对拍）
- **永远不要直接 `cout`**。先将最终输出结果拼接到一个字符串变量中（例如 `result`）。
- 在 `cout` 之前，**只用一次 `assert`** 验证该字符串是否与预期输出完全一致。
- 如果断言失败，程序立即崩溃，OJ返回 **RE** —— 这是测试失败的信号（用例触发了bug）。
- 如果断言成功，程序正常执行 `cout` 输出结果，OJ收到输出后开始比对。由于测试模式下输入是硬编码的，输出必然与OJ的测试数据不匹配，因此OJ会返回 **WA** —— 这是测试通过的信号（用例未触发bug，程序正常结束）。

**为什么只用一次断言？**  
训练的核心是让用户设计边界用例并观察是否触发bug。我们只关心最终输出是否正确，不关心中间过程。一次断言足够判断整个程序运行结果是否符合预期。多次断言会增加复杂性，且不是本次训练的重点。

### 5. 信号解读（关键）
用户在OJ上提交测试代码（宏开启）时，会看到：
- **WA**：程序正常结束，所有断言通过。说明用户设计的**用例未触发bug**（用例无效或bug不在该边界）。
- **RE**：程序崩溃，至少一个断言失败。说明用户设计的**用例成功触发了bug**（用例有效）。

这样，用户就能通过OJ返回的WA/RE来判断自己构造的用例是否有效。

### 6. 禁止输出额外信息
- 测试模式下，除了题目要求的输出外，**绝对不能输出任何调试信息、测试报告等**（如 `cout << "Test PASS"`）。这些输出会导致输出格式错误，使OJ统一判WA，从而丧失区分度。

## 三、为什么不能像 `sen.cpp` 那样写？

`sen.cpp` 的错误点：
- 宏默认开启，容易误提交。
- 用 `cout` 输出测试结果（如 `"Test FAIL at line ..."`），这些在OJ上看不到，且会干扰正常输出，导致OJ总判WA，无法区分“通过”和“失败”。
- 使用复杂的逻辑遍历所有输出行并逐行比较，最后输出总结，这些在OJ环境下毫无意义。
- 没有利用 `assert` 触发RE作为测试失败的信号，丧失了区分度。

## 四、绝对正确的范例（A+B问题）

```cpp
// A+B 问题示例（正确测试框架）
// 测试模式信号：WA = 用例通过（未触发bug），RE = 用例触发bug

// 选择测试用例集：取消注释下面一行，并将数字改为 1 或 2 等
// #define CASE 1

#include <iostream>
#include <sstream>
#include <cassert>
using namespace std;

int main() {
    int a, b;
    string result;          // 用于暂存最终输出

#ifdef CASE
    // ========== 根据 CASE 值选择测试数据 ==========
    string test_input;
    string expected_output;

#if CASE == 1
    test_input = "3 5\n";
    expected_output = "8\n";
#elif CASE == 2
    test_input = "100 200\n";
    expected_output = "300\n";
#else
#error "Unsupported CASE value"
#endif

    // 重定向输入流
    istringstream iss(test_input);
    cin.rdbuf(iss.rdbuf());
#endif

    // ========== 核心计算逻辑（完全不变） ==========
    cin >> a >> b;
    int sum = a + b;
    result = to_string(sum) + "\n";        // 将输出暂存

#ifdef CASE
    // ========== 输出前断言（仅一次） ==========
    assert(result == expected_output);     // 失败则触发 RE
#endif

    // ========== 实际输出 ==========
    cout << result;                        // 断言通过后才输出

    return 0;
}
```

### 代码解释
- **宏控制**：`// #define CASE 1` 默认注释，用户取消注释并修改数字来选择用例集。
- **多用例选择**：通过 `#if CASE == 1` 等分支定义不同测试数据。
- **输入重定向**：测试模式下，将 `cin` 绑定到 `test_input` 字符串流。
- **核心计算**：与普通A+B代码完全一致，结果存入 `result`。
- **断言**：在 `cout` 前用 `assert` 验证 `result` 是否等于 `expected_output`。这是整个测试框架中唯一的断言。
- **输出**：断言通过后执行 `cout`，输出结果。

### 运行效果
- 本地运行测试模式：断言通过则程序正常结束，输出 `8`；断言失败则程序崩溃（触发RE）。
- 提交到OJ（宏开启）：如果断言通过，OJ会判WA（因为输出与OJ测试数据不匹配）；如果断言失败，OJ判RE。用户通过WA/RE即可判断用例是否有效。

## 五、对AI agent的硬性要求

在编写任何题目代码时，必须严格遵守以下原则：

1. **宏开关默认注释**：确保正常提交的代码不含测试代码。
2. **多用例选择**：若需要多组测试数据，用 `#if CASE == n` 分支组织，每个分支定义 `test_input` 和 `expected_output`。
3. **输入重定向**：测试模式下，将 `cin` 绑定到 `test_input` 的字符串流。
4. **核心逻辑不变**：计算部分与普通AC代码完全一致，不得因测试模式而修改。
5. **输出暂存**：将最终输出结果拼接到一个字符串变量中（如 `result`）。
6. **单次断言**：在 `cout` 之前，用且仅用一次 `assert(result == expected_output)`。
7. **禁止额外输出**：测试模式下不得输出任何与题目无关的信息。
8. **注释说明**：在代码开头用注释说明测试模式的信号解读方式（WA=通过，RE=失败），方便用户理解。
