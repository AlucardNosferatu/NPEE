# AI Agent 任务要求：基于 Go To 标签范式（流程状态机范式）的 C++ 算法代码生成（最终版）

## 一、任务目标
根据用户提供的**算法名称**（上机考试常用算法），自主完成算法原理调研、逻辑拆解，最终输出符合 **更新版 Go To 标签范式** 的 C++ 可运行代码（含完整注释、测试主函数），确保代码功能正确、范式合规、可读性强，且强制记录算法输出前的最终收敛状态。

## 二、前置要求
1. 无需用户提供算法原理、伪代码等额外信息，AI Agent 需自主通过搜索工具获取目标算法的核心逻辑、输入输出格式、关键步骤、边界条件（如排序算法需支持空序列、重复元素；查找算法需支持有序/无序序列等）；
2. 严格遵循《Go To 标签范式（流程状态机范式）C++ 编程规范（更新版）》，所有代码必须符合新增规则（如`RETURN_RESULT`标签、最终状态断言、条件跳转规范），禁止违反核心要求；
3. 代码需能直接编译运行，测试主函数需包含至少 2 组测试用例（覆盖常规场景和边界场景），确保算法功能正确；
4. 强制要求：算法的`return`逻辑必须抽离为独立`RETURN_RESULT`标签，且前序必须添加最终状态断言，无论状态是否变化。

## 三、核心任务步骤（按优先级执行）
### 步骤 1：算法原理调研与拆解
1. 搜索目标算法的官方定义、核心思想、执行流程（如快速排序的"基准选择→分区→递归处理子序列"）；
2. 明确算法的输入（如 `vector<int>` 序列、目标值等）、输出（如排序后的序列、查找结果索引等）；
3. 拆解算法为"可标签化的动作单元"：按"单一职责"拆分核心操作（如初始化、搜索、交换、分区、栈操作等），并单独规划`RETURN_RESULT`标签（仅用于执行`return`）；
4. 识别算法的"状态变化节点"和"最终收敛状态"：
   - 状态变化节点：明确哪些动作执行后会修改核心变量（如索引、基准值、栈数据等），为常规状态断言做准备；
   - 最终收敛状态：明确算法输出前的合法状态（如排序序列有序、查找结果索引有效、动态规划最优解已计算等），为最终状态断言做准备；
5. 若算法含递归逻辑（如二叉树遍历、归并排序），需规划自定义栈的设计（存储子问题参数），禁止使用原生递归栈。

### 步骤 2：按更新版范式编写 C++ 代码
严格遵循以下编程规范（核心规则重申，需完全遵守）：

#### （1）标签设计
- **动作标签**：
  - 常规动作标签：全大写英文字母+下划线命名（如 `INIT`、`PARTITION`、`POP_STACK`），仅承载业务操作（变量初始化、计算、判断、栈操作等），无任何 `assert` 语句，无 `return` 逻辑；
  - 特殊动作标签：`RETURN_RESULT`（固定命名），仅包含`return`语句（如`return input_list;`），无其他业务逻辑，所有`return`必须集中在此标签；
- **状态标签**：
  - 常规状态标签：按 `STATE_数字` 格式命名（如 `STATE_1`、`STATE_6`），数字递增且唯一，仅含 `assert` 断言（验证核心变量合法性、预期值、数据关联性），无任何业务操作；
  - 最终状态标签：按 `STATE_数字` 或 `FINAL_STATE` 格式命名，仅含 `assert` 断言（验证最终收敛状态合法性），无论前序动作是否修改状态，必须添加；
- **标签拆分**：长动作必须拆分，即使连续动作无状态变化，也可按可读性需求拆分为独立动作标签，无需合并。

#### （2）动作与状态衔接
- **常规流程链路**：`动作A`→`STATE_X`（常规状态断言）→`动作B`→`STATE_Y`（常规状态断言）→...；
- **无状态变化的连续动作链路**：`动作A`→`动作B`→`动作C`→...（仅当无核心变量修改时允许）；
- **最终返回链路（固定强制）**：`最后一个业务动作`→`最终状态断言标签`（验证算法收敛状态）→`RETURN_RESULT`（执行`return`），禁止跳过最终状态断言直接返回；
- **重要补充规则**：
  - 状态标签内允许通过条件进行条件断言（如 `if` 条件），但跳转只有1个目标动作（状态决定的下一步动作是必然唯一的，否则状态划分不够细）；
  - 如果在执行流程上有分支操作，则延后到跳转后的动作进行分支；
  - 动作标签内允许条件跳转，但同一动作标签下，不同条件的跳转对象要么都是状态，要么都是动作，不允许在同一动作标签下用条件跳转状态和动作。

#### （3）条件跳转规则详解
1. **状态单跳模式**：
   ```cpp
   STATE_0:
       // 状态断言...
       goto ACTION_A; // 唯一的目标动作标签
   ```
   - 状态标签内只有`assert`断言和唯一的`goto`跳转
   - 状态决定的下一步动作是必然唯一的，否则状态划分不够细
   - 在流程图中：状态框图→动作箭头

2. **动作分支跳动作模式**：
   ```cpp
   ACTION_A:
       if (condition) {
           goto ACTION_B; // 跳转到动作标签
       } else {
           goto ACTION_C; // 跳转到动作标签
       }
   ```
   - 动作标签内可以有条件判断和多个`goto`跳转
   - 所有跳转目标都是动作标签（类型一致）
   - 在流程图中：动作→菱形块（if块）→不同动作箭头

3. **动作分支跳状态模式**：
   ```cpp
   ACTION_A:
       if (condition) {
           goto STATE_1; // 跳转到状态标签
       } else {
           goto STATE_2; // 跳转到状态标签
       }
   ```
   - 动作标签内可以有条件判断和多个`goto`跳转
   - 所有跳转目标都是状态标签（类型一致）
   - **禁止混合跳转**：不能在同一动作标签下有的条件跳转到状态，有的条件跳转到动作
   - 在流程图中：动作→菱形块（if块）→同名动作箭头指向不同状态框图

#### （4）状态断言设计
- **常规状态断言**：每个"状态变化节点"对应一个常规状态标签，断言内容包含：
  - 变量合法性（如索引在有效范围、栈长度一致、数值非负）；
  - 变量预期值（如初始状态 `start_index=0`、交换后 `swap_happened=true`）；
  - 数据关联性（如基准值存在于当前序列、子序列不超出原序列范围）；
- **最终状态断言**：强制验证算法输出的合法性，示例如下：
  - 排序算法：断言序列有序（`input_list[k] >= input_list[k-1]`）、输出长度与输入一致；
  - 查找算法：断言找到时索引在有效范围、未找到时索引为 `-1`（或约定值）；
  - 动态规划算法：断言最优解非负（或符合业务逻辑）、状态转移结果正确；
- **断言错误信息格式**：`assert(条件 && "STATE_数字: 错误原因")`（如 `assert(input_list[k]>=input_list[k-1] && "STATE_7: 输出序列未按升序排序")`）。

#### （5）变量与数据管理
- 核心变量（如序列长度、索引、基准值、栈、结果标记等）在函数开头或入口动作标签中集中声明；
- 临时变量（如交换用的 `temp`、循环计数器）可在动作标签内局部声明，无需断言；
- 自定义栈需明确存储的子问题参数（如子序列起始索引、长度、基准点等），栈操作（`push`/`pop`）需放在独立动作标签中。

### 步骤 3：添加完整注释
1. **函数注释**：函数上方说明算法名称、功能、输入参数、输出参数（如 `// 快速排序：对输入vector<int>排序，返回升序序列`）；
2. **标签注释**：
   - 常规动作/状态标签：上方用 1-2 行说明功能（如 `// 动作：初始化排序核心参数`、`// 状态：验证初始参数合法性`）；
   - `RETURN_RESULT` 标签：上方注释说明"专门执行算法最终返回"；
   - 最终状态标签：上方注释明确"验证算法最终收敛状态合法性"；
3. **复杂逻辑注释**：关键步骤（如交换逻辑、分区规则、栈弹出顺序）需补充行内注释，说明设计意图；
4. **断言注释**：通过 `assert` 的错误信息明确验证目的，无需额外添加注释。

### 步骤 4：代码功能验证
1. **编写 `main` 函数**：包含至少 2 组测试用例（如排序算法测试"常规序列"和"空序列/重复元素序列"，查找算法测试"目标存在"和"目标不存在"）；
2. **测试逻辑**：调用算法函数，打印输入和输出结果，验证代码执行正确性；
3. **兼容性检查**：确保代码无语法错误，可直接用 C++ 编译器编译运行（需引入必要头文件，如 `<vector>`、`<cassert>`、`<algorithm>` 等）；
4. **范式合规检查**：
   - 确认`RETURN_RESULT`标签唯一、最终状态断言存在、无嵌入式`return`逻辑；
   - 确认状态标签跳转唯一性（单跳）；
   - 确认动作标签内条件跳转的一致性（要么全跳状态，要么全跳动作）。

## 四、输出要求
1. **完整 C++ 代码**：包含算法函数（含`RETURN_RESULT`标签和最终状态断言）、测试主函数，严格遵循更新版范式规范，无任何违规写法；
2. **注释覆盖率**：函数、标签（含`RETURN_RESULT`和最终状态标签）、复杂逻辑均有注释，确保用户能快速理解代码结构和断言目的；
3. **测试用例说明**：在 `main` 函数中用注释说明每组测试用例的目的（如 `// 测试用例1：常规无序序列`）；
4. **格式规范**：代码缩进一致（建议 4 个空格），标签单独成行，全大写；`goto`语句后紧跟目标标签，不换行；断言语句按"变量条件+错误信息"格式对齐，提升可读性。

## 五、禁忌事项（禁止违反）
1. 禁止未调研算法原理直接编写代码，确保逻辑符合算法官方定义；
2. 禁止在状态标签中添加业务操作代码，或在常规动作标签中添加 `assert` 语句、`return` 逻辑；
3. 禁止未抽离`RETURN_RESULT`标签，或`return`逻辑嵌入其他动作标签；
4. 禁止在`RETURN_RESULT`前未添加最终状态断言，或最终状态断言未验证算法输出合法性；
5. 禁止状态标签命名不遵循 `STATE_数字` 格式，或`RETURN_RESULT`标签命名不规范；
6. 禁止递归算法使用原生递归栈，必须用自定义栈实现；
7. 禁止代码无注释、无测试用例，或测试用例未覆盖边界场景；
8. 禁止代码无法编译运行，或功能不符合算法预期；
9. **禁止状态标签内有多于一个`goto`跳转，或状态标签内使用条件跳转**；
10. **禁止动作标签内混合跳转状态和动作类型的目标**；
11. 禁止空动作标签（只包含`goto`而无其他操作的标签是允许的，但需确保其必要性）。

## 六、任务二补充说明：C++ 代码注释强化要求
### 1. 补充目的
为确保后续处理"单个动作标签+代码""单个状态标签+断言"的AI Agent能准确理解代码逻辑（包括操作目的、全局含义、变量约束等），避免因上下文缺失导致出题错误，需在原有代码生成规则基础上，强化注释要求，允许高密度注释（不影响代码编译运行）。

### 2. 具体注释规则（强制要求，与原有任务二规则并行执行）
#### （1）注释密度与范围
- 允许"一行代码+多行注释"：单个代码行（包括变量声明、逻辑判断、`goto`跳转、栈操作、断言等）可搭配1-3行注释，无最低注释要求，但需确保关键逻辑无歧义；
- 覆盖所有核心代码：
  - 动作标签内的每一步业务操作（如变量赋值、`if-else`判断、`push/pop`栈操作、`goto`跳转）；
  - 状态标签内的每一条`assert`断言（需解释断言的依据、状态特征的含义）；
  - 核心变量声明（需说明变量的用途、全局作用、与其他模块的关联）。

#### （2）注释内容要求
- **动作标签代码注释**：需包含"操作目的""变量含义""全局逻辑关联"（如该操作在整个算法中的作用），示例：
  ```cpp
  // 目的：从栈中弹出子序列的长度、起始索引、基准点索引（子问题参数）
  // 变量关联：ss_stack存储子序列长度，si_stack存储起始索引，pivot_stack存储基准点索引
  // 全局作用：更新当前处理的序列信息，为下一轮排序迭代做准备
  seq_size = ss_stack.back();
  ss_stack.pop_back();
  start_index = si_stack.back();
  si_stack.pop_back();
  pivot_index = pivot_stack.back();
  pivot_stack.pop_back();
  ```
- **状态标签断言注释**：需包含"断言依据""状态特征含义""约束目的"，示例：
  ```cpp
  // 断言依据：排序算法的最终收敛状态要求序列按升序排列
  // 状态特征：任意相邻元素满足后一个>=前一个（非降序）
  // 约束目的：确保输出结果符合算法预期，避免排序失败
  assert(input_list[k] >= input_list[k-1] && "STATE_7: 输出序列未按升序排序");
  ```
- **变量声明注释**：需包含"变量用途""数据来源""生命周期"（如局部变量/全局变量、是否参与跨动作传递），示例：
  ```cpp
  vector<int> ss_stack; // 用途：存储需要排序的子序列长度（子问题参数）；数据来源：DIVIDE_SORT动作压栈；生命周期：整个算法执行期间
  ```

#### （3）格式规范
- 注释需用`//`开头，与代码缩进保持一致（建议代码缩进4个空格，注释缩进与对应代码相同）；
- 多行注释时，按"核心逻辑→细节补充→全局关联"的顺序编写，避免冗余重复；
- 注释语言为中文，表述清晰直白，避免专业术语堆砌，确保AI Agent能直接理解。

#### （4）兼容性要求
- 注释不影响代码编译运行：仅添加说明性文字，不修改任何代码逻辑、变量名、标签名；
- 不改变原有范式规则：所有注释要求与原有"动作与断言解耦""标签命名规范""最终状态断言"等规则并行执行，无冲突。

### 3. 示例参考（符合注释要求的代码片段）
```cpp
SEARCH_START:
    // 目的：重置双指针与交换标记，为新一轮元素查找与交换做准备
    // 变量重置逻辑：i从当前序列起始索引开始，j从基准点索引+1开始（分区查找范围）
    // 全局关联：该动作是排序迭代的核心初始化步骤，承接上一轮交换/分割结果
    swap_happened = false; // 交换标记重置为false：初始状态未发生元素交换
    i = start_index; // 左指针i：指向当前序列起始位置
    j = pivot_index + 1; // 右指针j：指向基准点右侧第一个元素（开始查找大于基准的元素）
    goto STATE_2; // 跳转至双指针初始化断言：验证指针位置合法性

STATE_7:
    // 断言依据：快速排序的最终收敛条件（输出序列非降序、长度与输入一致）
    // 状态特征1：序列长度不变（排除排序过程中数据丢失/冗余）
    assert(input_list.size() == seq_size && "STATE_7: 输出序列长度与输入不一致");
    // 状态特征2：所有相邻元素满足非降序（核心排序结果验证）
    // 约束目的：确保算法执行完毕后输出合法，避免未排序完成就返回
    for (int k = 1; k < input_list.size(); k++)
    {
        assert(input_list[k] >= input_list[k-1] && "STATE_7: 输出序列未按升序排序（最终状态非法）");
    }
    goto RETURN_RESULT;
```

## 七、新增规则关键点总结
1. **状态标签单跳规则**：每个状态标签必须有且仅有一个`goto`跳转，指向一个动作标签，确保状态到动作的映射是唯一的。
2. **动作标签跳转一致性规则**：同一个动作标签内的条件跳转，所有跳转目标必须是同类型的（要么都是状态标签，要么都是动作标签），不能混合。
3. **流程图对应关系**：
   - 状态：矩形框图
   - 动作：箭头
   - 条件分支：菱形块（决策点）
   - 动作分支跳动作：动作→菱形块→不同动作箭头
   - 动作分支跳状态：动作→菱形块→同名动作箭头指向不同状态框图
4. **最终状态合并规则**：如果某个状态已经是最终返回前的最后状态，不要单独分出一个`FINAL_STATE`，直接将该状态重命名为`FINAL_STATE`，所有验证逻辑都写在这个标签下。

## 八、设计思维与最佳实践（新增部分）

### 1. 设计优先级原则
- **业务逻辑优先**：先深入理解算法本质，识别真正的状态变化和业务操作，再适配范式结构，而不是让业务逻辑强行适应范式。
- **简化优先于对称**：当分支逻辑不对称时，优先保证代码简洁性和清晰性，不必强求所有分支都有对等的标签数量。
- **状态驱动流程**：允许状态标签直接跳转到有意义的动作标签，即使这使得分支不对称，状态决策本身就是流程的一部分。

### 2. 避免空动作标签的设计检查
在创建动作标签时，必须进行必要性检查：
- **操作验证**：该标签是否执行了有意义的业务操作（如变量赋值、计算、栈操作等）？
- **状态变化验证**：该标签是否改变了算法核心状态？
- **流程必要性验证**：如果没有这个标签，流程是否同样清晰？
- **对称性质疑**：创建这个标签是为了解决实际问题，还是仅仅为了满足形式上的对称性？

### 3. 状态标签的扩展职责
状态标签不仅是验证工具，还可以：
- **表达决策逻辑**：通过断言验证的状态特征可以直接决定下一步操作
- **驱动流程方向**：状态标签可以根据已验证的状态特征，直接跳转到适当的动作标签
- **封装条件分支**：当分支决策基于已验证的状态时，状态标签可以直接跳转到不同分支

### 4. 标签设计的实用指南
1. **先识别真正的状态变化点**：只有核心变量被修改时才需要状态断言
2. **为每个有意义的业务操作创建动作标签**：即使操作简单，只要它是算法逻辑的必要步骤
3. **允许状态标签直接跳转**：当状态已经明确指示了下一步操作时，不需要额外的"决策动作"
4. **质疑每个标签的存在价值**：定期回顾标签结构，确保每个标签都有明确的、不可替代的职责
5. **保持标签职责单一**：一个标签只做一件事（要么验证状态，要么执行操作）

### 5. 常见陷阱及避免方法
- **对称性陷阱**：避免为了分支对称而创建不必要的标签。分支不对称往往是业务逻辑的真实反映。
- **过度拆分陷阱**：避免将单一逻辑拆分成过多标签，导致流程碎片化。保持合理的粒度。
- **空动作陷阱**：当发现需要创建只有`goto`的动作标签时，重新审视是否可以：
  a) 让状态标签直接跳转到目标动作
  b) 合并相邻标签
  c) 重新设计流程结构
- **状态冗余陷阱**：避免为没有实际状态变化的节点创建状态标签。只有核心变量变化时才需要状态验证。

### 6. 设计审查清单
完成代码后，必须检查：
1. 每个状态标签是否有且仅有一个`goto`跳转？
2. 每个动作标签内的条件跳转是否目标类型一致？
3. 是否存在只有`goto`的动作标签？如有，是否必要？
4. 最终状态断言是否完整验证了算法收敛条件？
5. 所有分支是否都正确处理？是否存在遗漏的边界情况？
6. 注释是否充分解释了每个标签的职责和逻辑关联？
7. 测试用例是否覆盖了常规场景和边界场景？
