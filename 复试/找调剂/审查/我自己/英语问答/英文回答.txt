I built this automatic programming Agent based on LangFlow, 
a Python-based DAG workflow framework, 
and used the Qwen-3 7 billion parameters large language model.
【精简版】
The agent follows a multi-agent collaborative pipeline: 
it first parses user queries through prompt engineering, 
designs software requirements, 
generates Python code, 
executes the code via a Python execution tool, 
and finally summarizes results to complete the task.
A key limitation of such DAG-based frameworks is that they cannot send feedback to earlier agents for rework, even if the task fails.
【详细版】
Through prompt engineering, 
Agent 1 first parses user input into a problem to be solved, 
then converts it into formatted text with problem premises and statements, 
and sends it to Agent 2 and Agent 5.
Agent 2 designs software requirements for solving or verifying the problem according to the formatted description, 
and passes them to Agent 3 and Agent 5.
Agent 3 generates corresponding Python code based on these requirements and sends the code to Agent 4 and Agent 5.
Agent 4 executes the Python code via the Python exection tool and returns the result to Agent 5.
Finally, Agent 5 judges whether the task is completed based on the summarized information and gives feedback to the user.
Due to the characteristics of DAG, 
Agent 5 still has to reply to the user even if the task is not successfully completed, 
which is a typical limitation of DAG-based workflow frameworks like LangFlow.
我基于LangFlow（一个基于Python的DAG工作流框架）构建了这个自动编程代理，
并使用了拥有70亿参数的Qwen-3大型语言模型。
【精简版】
该代理遵循多代理协作流程：
首先通过提示工程解析用户查询，
设计软件需求，
生成Python代码，
通过Python执行工具执行代码，
最后汇总结果以完成任务。
此类基于DAG的框架的一个主要局限性在于，即使任务失败，它们也无法向之前的代理发送反馈以进行返工。
【详细版】
通过提示工程，
代理 1 首先将用户输入解析为待解决的问题，
然后将其转换为包含问题前提和陈述的格式化文本，
并将其发送给代理 2 和代理 5。
代理 2 根据格式化描述设计解决或验证问题的软件需求，
并将其传递给代理 3 和代理 5。
代理 3 基于这些需求生成相应的 Python 代码，并将代码发送给代理 4 和代理 5。
代理 4 通过 Python 执行工具执行 Python 代码，并将结果返回给代理 5。
最后，代理 5 根据汇总信息判断任务是否完成，并向用户提供反馈。
由于 DAG 的特性，
即使任务未成功完成，代理 5 仍然需要回复用户，
这是基于 DAG 的工作流框架（例如 LangFlow）的典型局限性。

Tasks or threads in an RTOS are quite different from processes in general operating systems as mentioned in the 408 syllabus.
For efficiency, many RTOS adopt a thread model, where all tasks can freely access the entire memory space.
In terms of scheduling, 
they widely use cooperative scheduling mechanisms like coroutines with autonomous features, 
instead of being fully controlled by the kernel.
This enables flexible scheduling for urgent task chains.
These distinct designs from general OS taught me that I should analyze specific problems case by case, 
rather than rigidly applying fixed rules to research objects.
正如408课程大纲所述，实时操作系统（RTOS）中的任务或线程与通用操作系统中的进程截然不同。
为了提高效率，许多RTOS采用线程模型，其中所有任务都可以自由访问整个内存空间。
在调度方面，
它们广泛使用具有自治特性的协程等协作调度机制，
而不是完全由内核控制。
这使得紧急任务链能够进行灵活的调度。
这些与通用操作系统截然不同的设计让我明白，我应该针对具体问题逐一分析，
而不是生硬地将固定的规则应用于研究对象。
